# Message coverage audit

Audit date: 2026-09-30. Source baseline: `ce6763d3`, on `feat/ctrace-compact-csv-messages`.
This is the pre-implementation source audit. Its line references and coverage findings describe the baseline above.
The subsequent [message-system design](message-system-design.md) includes the implemented trace and CLI-only catalogs.

## Result and scope

The [message-system design](message-system-design.md) covers all four CSV diagnostic output paths:
decoder issues, skipped bytes, fatal decoder aborts, and overflow. The scan found no additional CSV diagnostic
writer. The API sketch and transport plan needed the additions below to preserve all detailed CLI wording.

The original proposal left CLI-only diagnostics outside the trace-message catalog. The implemented design now
centralizes their ctrace-owned wording in `DiagnosticMessages`, separately from the shared `TraceMessages`
catalog. Both catalogs preserve foreign detail as opaque text. The inventory below records the original
sources and behavior, including the deferred messages that needed migration.

The scan covered the 84 C++ implementation/header files under `tools/ctrace/src`, including producers, exception
classes, catches, deferred validation fields, callbacks, and final writers. References to tests and the vendored
OpenCSD logger were checked where they clarify boundaries. Build/release/fixture scripts are outside the ctrace
runtime message system. CTF/XML schema labels, CSV headers, and help/version text are not diagnostics.

## Baseline findings incorporated into the design

1. Add an explicit formatter for `OverflowTraceEvent`, plus a separate `TraceOverflowSummary` carrying the optional
   first timestamp and event count. CSV renders each event; CLI reports one aggregate per internal route.
2. Carry typed issue detail through the collector's current string-taking APIs and `OpenCsdTraceElement` into
   `TraceIssueEvent`. Changing the final formatter signatures alone would leave most parameters lost in prose.
3. Store resumed timestamps structurally. `CortexMPostDecoder` currently appends the range to `issue.message`;
   `lastValidTcyc` alone is insufficient for reproducing both forms.
4. Model initialization/setup failures across `OpenCsdTreeSessionError` / `OpenCsdItmSessionError`. Their own
   operation/object/error wording must move to the catalog, even when the compact result is simply
   `OpenCSD initialization failed`. Preserve native error details separately.
5. Carry abort phase and structured cause through `OpenCsdFatalError` into `TraceDecodeAbort`. Today the exception
   carries only a rendered message and a byte count, and `FileDecodeJob` copies `what()` into `reason`. Include
   DATA, end-of-trace, WAIT flushing, formatted draining, SINGLE reset, and formatted route-reset contexts;
   preserve each current detailed prefix. Unknown exception detail still needs a text fallback.
6. Treat packet context as ctrace-owned formatting: packet kind, size, bounded byte preview, unavailable bytes,
   and truncation. Use a typed `PacketContext` or a dedicated detailed formatter in the central module. It is
   different from the opaque text generated by OpenCSD itself.

## Sink and exception boundaries

The only direct runtime diagnostic stream writer in ctrace is
[StderrDiagnosticSink](../src/diagnostics/DiagnosticSink.cpp), line 58. It adds severity/context and counts failure
impact separately. Help/version use stdout in `CtraceMain`; they do not go through the diagnostic catalog.

Only `OpenCsdFatalError` is converted into `TraceDecodeAbort` in
[FileDecodeJob.cpp](../src/control/FileDecodeJob.cpp), lines 271–279. An ordinary input read error or other exception
reaching the generic job catch produces a CLI diagnostic instead. Backend exceptions are handled by
`TraceOutputLifecycle` and remain CLI diagnostics. Preserve these distinctions during a wording refactor.

CTF writes structured status reasons such as overflow, data loss, and decode error, not the rendered issue text;
see [CtfEncoder.cpp](../src/output/ctf/CtfEncoder.cpp), lines 206–235. No new CTF text formatter is needed. CSV's
`CPU Sleeping` and `Trace prohibited` notes are existing PC states, not diagnostics.

OpenCSD's default logger has no output logger installed by ctrace. Native `LogError` callbacks are captured and
warning/error events are forwarded; `LogMessage` and informational callbacks are not a separate visible info
output path. Informational callback detail can still be selected for an existing failing root-response summary.
Do not add standalone info output; preserve the existing response/error fallback behavior, including that detail.

## CLI-only catalog requirements implemented by DiagnosticMessages

Extend the catalog with CLI-only families for argument, configuration/location, processor/route binding, path/IO,
backend lifecycle, and run-summary messages. These need detailed templates only; adding CSV variants would not
create a valid CSV output path. Keep their data separate from `TraceIssueEvent`, which represents a decoder issue.

Preserve an explicit text pass-through path for externally supplied reference diagnostics, YAML/cxxopts/native
OpenCSD text, OS errors, and unknown exceptions. Centralize ctrace-owned wrappers while keeping foreign detail
opaque. Deferred validation fields must participate as well as immediate `report` and `throw` sites. Severity,
failure impact, location and context remain independent of the wording.

## Validation after implementation

Verify each of the four CSV paths and the unchanged detailed CLI output, including overflow aggregation,
timestamp completion, initialization failures, fatal phases, native fallback detail and packet previews. Retain
filter-independent skip/abort tests and source-route attribution. Add regression coverage at collector and
exception boundaries so typed parameters survive all intermediate representations.

The initial scan changed documentation only. The subsequent implementation adds catalog and transport regression
tests and preserves the existing CLI expectations; its validation is described in the message-system design.
